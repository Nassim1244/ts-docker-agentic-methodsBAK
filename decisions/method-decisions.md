# Method decisions

Read this before proposing or changing anything about how the methods are designed.
- Each line is a decision currently in force that constrains future work, with the options it rejected.
- The explanation for each is in `method-rationale.md`, under the same ID. Open that file only when changing a decision.
- Log a decision here only if a future session could break it without knowing. Otherwise it belongs in `journal/`.
- When a decision is superseded, remove its line from this file. Its rationale entry stays, and the entry for the new decision names the one it supersedes.
- IDs are `MD-nnn`, allocated in order and never reused.
- If this file grows past about 40 lines, alert the user: some lines probably belong in a rule or should be superseded.

- MD-001 The workbench holds independent, self-contained templates named by philosophy and versioned with git tags per template. Rejected: evolving v3 in place, one shared ai-rules with two workflows, folders named by version.
- MD-002 Decisions are recorded in two files per domain: a short log (one line per binding decision, with what it rejected) and a rationale file. The domains are FD in `specs/functional/`, AD in `specs/technical/`, DD in `design/`, and MD in the workbench `decisions/`. Rejected: one long decisions.md read by every agent, one file per decision.
- MD-003 Both templates support cloud sessions on `cloud/<type>/<x>` branches. A spec (gated) or a feature (batch) is claimed by one unmerged session at a time. In batch, local sessions stay on trunk; a cloud branch rebases on main and fast-forwards, re-running the cycle-exit gates only if main moved. Rejected: trunk-only with no cloud, cloud in gated only, PR plus human merge, batch branches, claiming the whole batch or trunk, no claim, always re-running gates.
- MD-004 The cloud environment gets a minimal setup script (pinned Node and pnpm, frozen install, `prisma generate`), enough for the machine gates. No Docker or e2e in the cloud. Rejected: replicating the devcontainer, documenting the gap only.
- MD-005 In batch, the architect sets the whole batch's schema before the cycles and can be called back during the batch. A migration on a session branch triggers an automatic AI architect check before any merge, fast-forward or not, and its commit carries `Risk: schema`. Rejected: regenerating migrations on rebase, serialising schema features, a human stop per migration.
- MD-006 An app's product AD enters a template only as a generic stack convention: one policy rule plus one AD line in the template's own sequence. From Synfactu: AD-023, AD-031 (with AD-033 as its exception clause), AD-034, AD-035, AD-020, and AD-025 to AD-028 merged into one line. AD-018 stays Synfactu-only, and the money/duration value-object init step becomes conditional. Rejected: Synfactu numbering, one line per Synfactu AD, fix-only without an AD, template defaults for rounding and day length, a mandatory money init step.
- MD-007 `batch-design-workflow/` is the active method, meant to be brought to Synfactu. `spec-gated-workflow/` takes a one-time import of Synfactu's method 4.1.0 (product content stripped, MD-006 applied, `/force` and gate names back-ported), tagged v4.0.0, then frozen. Batch forks from that tag. Later shared fixes land in batch only and are logged in `journal/backlog-gated.md`. Rejected: forking from the current template, forking straight from Synfactu, maintaining gated in parallel.
